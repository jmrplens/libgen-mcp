`libgen-mcp` se publica en casi todos los sitios de los que ya sacas software. Elijas el que elijas acabas con el mismo ejecutable único: no se compila nada, no se ejecuta ningún script al instalar y ninguno de ellos necesita cuenta, clave de API ni token.

Esta página compara los canales y reúne lo que tienen en común. Cada canal tiene su propia página con los pasos para instalarlo, verificarlo, actualizarlo, fijar una versión y quitarlo. Para el camino más corto hasta un cliente que funcione, ve a [Primeros pasos](/libgen-mcp/es/getting-started/).

## Elige un canal

| Canal                                                                | Ejecútalo sin instalar                                  | Instálalo                                                        | Necesita                    | Plataformas                            |
| -------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------- | -------------------------------------- |
| [npm](/libgen-mcp/es/install/npm/)                                   | `npx -y @jmrp.io/libgen-mcp`                            | `npm install -g @jmrp.io/libgen-mcp`                             | Node 18 o posterior         | Linux, macOS, Windows; x64 y arm64     |
| [PyPI](/libgen-mcp/es/install/pypi/)                                 | `uvx libgen-mcp`                                        | `pipx install libgen-mcp`                                        | Python 3.9 o posterior      | Linux, macOS 11+, Windows; x64 y arm64 |
| [NuGet](/libgen-mcp/es/install/nuget/)                               | `dnx libgen-mcp`                                        | `dotnet tool install -g libgen-mcp`                              | SDK de .NET 10              | Linux, macOS, Windows; x64 y arm64     |
| [Homebrew](/libgen-mcp/es/install/homebrew/)                         | —                                                       | `brew install jmrplens/tap/libgen-mcp`                           | Homebrew                    | macOS y Linux; x64 y arm64             |
| [Docker](/libgen-mcp/es/install/docker/)                             | `docker run -i --rm ghcr.io/jmrplens/libgen-mcp:latest` | —                                                                | Docker o un runtime OCI     | Imágenes `linux/amd64` y `linux/arm64` |
| [Binario de la release](/libgen-mcp/es/install/binary/)              | —                                                       | descárgalo y ponlo en tu `PATH`                                  | Nada                        | Linux, macOS, Windows; amd64 y arm64   |
| [Go](/libgen-mcp/es/install/binary/#compilar-desde-el-código-fuente) | —                                                       | `go install github.com/jmrplens/libgen-mcp/v2/cmd/server@latest` | Go 1.27.1 o posterior       | Donde compile Go                       |
| [Claude Desktop](/libgen-mcp/es/install/claude-desktop/)             | —                                                       | abre el archivo `.mcpb`                                          | Claude Desktop              | macOS, Windows, Linux (beta)           |
| [Plugin para agentes](/libgen-mcp/es/install/agent-plugin/)          | —                                                       | el instalador de plugins de tu host                              | Un host de plugins y Docker | Donde funcionen el host y Docker       |

Si te da igual: **`npx` si ya tienes Node 18 o posterior, y Docker si no.** Ninguno de los dos instala nada que tengas que acordarte de actualizar. Si usas Claude Desktop y nada más, la extensión es un clic. Para probar el servidor antes de instalar nada, el [endpoint alojado](/libgen-mcp/es/hosted/) solo necesita un cliente.

**El servidor nunca se actualiza solo**, en ningún canal. Las actualizaciones vienen de lo que lo instaló: `npm`, `pipx`, `dotnet tool update`, `brew upgrade`, una imagen más nueva, un paquete más nuevo o una descarga nueva. `libgen-mcp --version` imprime lo que tienes.

## Lo que comparten todos los canales

- **El mismo binario.** Los gestores de paquetes de arriba no construyen nada. Cada uno lleva el binario de la release para tu plataforma y lo pone en una ruta, así que los bytes son los mismos viniera por donde viniera, y la procedencia de compilación de la release verifica cada uno de ellos. Dos excepciones: [`go install`](/libgen-mcp/es/install/binary/#compilar-desde-el-código-fuente) compila desde el código fuente, y la [imagen Docker](/libgen-mcp/es/install/docker/) compila el mismo código en su propia etapa de compilación.
- **No se ejecuta nada al instalar.** Ni script de postinstalación, ni compilador, ni descarga de red más allá del propio paquete.
- **Sin credenciales.** Library Genesis no necesita ninguna, y tampoco ninguno de los proveedores de acceso abierto a los que recurre el servidor. Hay claves para dos fuentes opcionales y son voluntarias; ver [Configuración](/libgen-mcp/es/configuration/).
- **Sin libc.** El binario se construye con `CGO_ENABLED=0` y **sin** `-buildmode=pie`, así que no nombra ningún cargador dinámico: el mismo archivo corre sobre glibc y sobre musl, en una imagen distroless y en `scratch`. Por eso también las wheels de PyPI pueden llevar honestamente etiquetas `musllinux` y ningún paquete de npm declara `libc`.
- **Seis plataformas.** Linux, macOS y Windows, en amd64 y arm64. Cualquier otra tiene que compilar desde el código fuente.
- **Las licencias viajan con él.** Los paquetes de npm, PyPI y NuGet, el paquete de Claude Desktop, la imagen (bajo `/usr/share/licenses/libgen-mcp`) y la fórmula de Homebrew llevan `LICENSE` y `THIRD_PARTY_NOTICES`. Un binario descargado suelto, o por winget, no; desde la 2.1.0 cada release publica `THIRD_PARTY_NOTICES` como asset propio.

**Lo que escribe en tu máquina**, lo haya instalado el canal que lo haya instalado:

| Ruta                                                   | Qué guarda                                                                                |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| `<dir. de caché del SO>/libgen-mcp/mirrors.json`       | La lista descubierta de mirrors de Library Genesis, cacheada 24 horas. Solo URLs públicas |
| `<dir. de caché del SO>/libgen-mcp/annas-mirrors.json` | Lo mismo para los mirrors de Anna's Archive                                               |
| Tu directorio de descargas                             | Lo que haya guardado `download`, allí donde apunte `LIBGEN_MCP_DOWNLOAD_DIR`              |
| El directorio temporal del sistema                     | Las copias de trabajo de `read`, desalojadas por un tope de tamaño y un TTL               |
| `~/.libgen-mcp.env`                                    | Ajustes, si lo creaste tú. Nada lo crea por ti                                            |

El directorio de caché es `~/.cache` en Linux, `~/Library/Caches` en macOS y `%LocalAppData%` en Windows. Borrar cualquiera de esas cosas solo fuerza una descarga nueva. Desinstalar por cualquier canal lo deja todo en su sitio.

**Actualizar un servidor que un cliente ya tiene en marcha.** Sustituir el binario por debajo de un proceso vivo deja al viejo reteniendo una plaza de descarga, una entrada de caché temporal y, en modo HTTP, el listener que quiere el nuevo. `libgen-mcp --shutdown` pide a todas las demás instancias de este binario en la máquina que salgan y mata lo que quede a los cinco segundos, así que la secuencia de actualización es: instalar, `--shutdown`, y dejar que el cliente lo arranque otra vez.

## Verificar lo que instalas

Cada release va firmada, y lo que eso te da depende del canal. La página de cada canal tiene las órdenes:

| Canal                                                                                | Qué se puede verificar                                                                                | Quién lo comprueba               |
| ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | -------------------------------- |
| [Binario de la release](/libgen-mcp/es/install/binary/#verificar-lo-que-instalaste)  | Un bundle de Sigstore sobre `checksums.txt`, más procedencia SLSA por cada asset                      | Tú                               |
| [Claude Desktop](/libgen-mcp/es/install/claude-desktop/#verificar-lo-que-instalaste) | Procedencia SLSA por paquete (los paquetes no están en `checksums.txt`)                               | Tú                               |
| [Docker](/libgen-mcp/es/install/docker/#verificar-lo-que-instalaste)                 | Una firma cosign sin claves sobre el índice y los dos manifiestos de plataforma, más procedencia SLSA | Tú                               |
| [npm](/libgen-mcp/es/install/npm/#verificar-lo-que-instalaste)                       | La procedencia de npm, adjuntada automáticamente porque la publicación es de un trusted publisher     | `npm audit signatures`           |
| [PyPI](/libgen-mcp/es/install/pypi/#verificar-lo-que-instalaste)                     | Attestations PEP 740, adjuntadas automáticamente por la misma razón                                   | Se ven en la página del proyecto |
| [NuGet](/libgen-mcp/es/install/nuget/#verificar-lo-que-instalaste)                   | La firma de repositorio de nuget.org, más procedencia SLSA por paquete (desde la 2.1.0)               | `dotnet nuget verify`, tú        |
| [Homebrew](/libgen-mcp/es/install/homebrew/#verificar-lo-que-instalaste)             | Un SHA256 por cada asset de plataforma, fijado en la fórmula                                          | El propio `brew`, al descargar   |
| [`go install`](/libgen-mcp/es/install/binary/#compilar-desde-el-código-fuente)       | La base de datos de checksums de Go, sobre el **código fuente**                                       | La cadena de herramientas de Go  |

**La firma es la mitad que se suele saltar, y es la que importa.** Un `checksums.txt` descargado de la misma página que el binario solo demuestra que los dos coinciden entre sí. El bundle de Sigstore demuestra que el manifiesto lo acuñó el workflow de release de este repositorio, y la firma es sin claves: no hay clave pública que distribuir, la identidad **es** el workflow, que es justo lo que fija `--certificate-identity-regexp` en las órdenes de cosign.

**La procedencia de compilación responde a otra pregunta**: qué commit y qué ejecución del workflow produjeron el archivo. Cada binario que instalan los gestores de paquetes es un asset de la release byte a byte, así que `gh attestation verify` lo comprueba allí donde haya quedado, y la página de cada canal dice dónde es. Dos flags hacen que la comprobación signifique lo que quieres:

- **`--signer-workflow jmrplens/libgen-mcp/.github/workflows/release.yml`.** `-R` por sí solo acepta una attestation acuñada por cualquier workflow del repositorio; este la ata al workflow de release. Todos los `gh attestation verify` de estas páginas lo llevan.
- **`--source-ref refs/tags/v<version>`.** Este la ata a la release que querías, de modo que una attestation válida de otra versión no pasa. Añádelo siempre que sepas la versión.

[cosign](https://docs.sigstore.dev/cosign/system_config/installation/) 3.x y la [CLI de GitHub](https://cli.github.com/) son las únicas herramientas que necesitan las comprobaciones. Un cosign 2.x dice «no signatures found» sobre una imagen que un cliente 3.x verifica.
