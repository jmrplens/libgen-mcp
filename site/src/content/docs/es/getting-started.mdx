`libgen-mcp` se publica en casi todos los sitios de los que ya instalas software: npm como [`@jmrp.io/libgen-mcp`](https://www.npmjs.com/package/@jmrp.io/libgen-mcp), PyPI como [`libgen-mcp`](https://pypi.org/project/libgen-mcp/), NuGet como herramienta .NET, el tap de Homebrew de este proyecto, un binario estático precompilado en la página de releases de GitHub, una imagen Docker (`ghcr.io/jmrplens/libgen-mcp`) o `go install`. No necesita cuenta, clave de API ni token. En cuanto queda registrado en un cliente MCP — Claude Code, Claude Desktop, Cursor o VS Code — sus cuatro herramientas (`search`, `get_details`, `download`, `read`) están disponibles de inmediato.

## Instalación

Todos los canales de abajo acaban en el mismo binario estático: no se compila nada y no se ejecuta nada al instalar. Si ya tienes Node 18 o posterior, **npm** es el camino más corto — un solo comando, y tu cliente MCP puede lanzar el servidor con `npx` sin instalar nada. Si no, elige el gestor de paquetes que ya uses, o coge el **binario precompilado**, que no necesita runtime de ningún tipo.

Lo que sigue es una orden por canal. **[Instalación](/libgen-mcp/es/installation/)** es la versión larga: una sección por canal con qué obtienes, cómo verificar que es lo que este proyecto publicó, cómo actualizarlo y cómo quitarlo.

		El servidor se publica en npm como [`@jmrp.io/libgen-mcp`](https://www.npmjs.com/package/@jmrp.io/libgen-mcp). Necesita Node 18 o posterior. El paquete es un lanzador ligero sobre los mismos binarios precompilados que sirve la página de releases: el ejecutable viaja dentro de un paquete por plataforma que npm desempaqueta solo cuando coinciden su `os` y su `cpu`, así que no se compila nada y no se ejecuta ningún script en la instalación. Como el ejecutable viaja dentro del paquete que npm descarga de todas formas, `npx` y `npm ci --ignore-scripts` funcionan igual, y también una instalación servida desde un mirror privado del registro — o desde la caché local con `--offline`, una vez que los tarballs están en ella.

    	Hay binarios precompilados para Linux, macOS y Windows en x64 y arm64. En cualquier otra plataforma el lanzador termina con un mensaje que apunta a los binarios del release y a la opción de compilar desde el código.
    </TabItem>
    <TabItem label="Binario">
    	Descarga un binario precompilado para tu plataforma desde la página de [releases de GitHub](https://github.com/jmrplens/libgen-mcp/releases). Los archivos se llaman `libgen-mcp-<os>-<arch>` (por ejemplo `libgen-mcp-linux-amd64` o `libgen-mcp-darwin-arm64`), cubriendo Linux, macOS y Windows en amd64 y arm64.

    	```bash
    	# Ejemplo: Linux amd64
    	curl -L -o libgen-mcp \
    	  https://github.com/jmrplens/libgen-mcp/releases/latest/download/libgen-mcp-linux-amd64
    	chmod +x libgen-mcp
    	sudo mv libgen-mcp /usr/local/bin/
    	```

    	El binario es totalmente estático (compilado con `CGO_ENABLED=0` y sin `-buildmode=pie`), así que no nombra ningún cargador dinámico, no depende de nada del host y arranca sin más — en glibc, en musl y en un contenedor distroless o `scratch`.

    	Cada release publica además un `checksums.txt` **y un bundle Sigstore que lo firma**, así que puedes comprobar que los bytes salieron del workflow de release de este proyecto y no solo que coinciden con un hash publicado a su lado. La receta son dos órdenes, y la primera — la firma sobre el manifiesto — es la que importa y la que se suele saltar: [Instalación → Verificar lo que instalas](/libgen-mcp/es/installation/#verificar-lo-que-instalas).
    </TabItem>
    <TabItem label="Docker">
    	¿Prefieres contenedores, o un comando sin instalación que tu cliente descarga en el primer arranque? Se publica una imagen multi-arch en el GitHub Container Registry:

    	```bash
    	docker pull ghcr.io/jmrplens/libgen-mcp:latest
    	```

    	La imagen **decide su transporte a partir de lo que sea la entrada estándar**, así que `docker run -i --rm ghcr.io/jmrplens/libgen-mcp:latest` (como lo usan los botones de un clic y `claude mcp add`) conecta una tubería y obtiene el servidor stdio, que es el modo correcto para un cliente MCP, y funciona sin configuración. Una ejecución sin `-i` — un servicio de Compose sin `stdin_open`, un pod de Kubernetes, cualquier cosa que arranque un orquestador — conecta `/dev/null` y obtiene en su lugar el listener HTTP en streaming en el puerto 8080. Monta un volumen con permisos de escritura para las descargas y apunta `LIBGEN_MCP_DOWNLOAD_DIR` a él; el contenedor se ejecuta como usuario sin privilegios, por lo que el directorio del host debe ser escribible por el UID `10001`:

    	```bash
    	docker run -i --rm \
    	  -v "$HOME/Downloads:/downloads" \
    	  -e LIBGEN_MCP_DOWNLOAD_DIR=/downloads \
    	  ghcr.io/jmrplens/libgen-mcp:latest
    	```

    	Pasa las variables que cambian el comportamiento de la misma forma — se combinan libremente. Activa los artículos de acceso abierto mediante Unpaywall, o consulta los buscadores extra (Anna's Archive, arXiv, Crossref, OpenLibrary, Project Gutenberg, dblp, PubMed, ERIC) en cada búsqueda (consulta la [referencia de configuración](/libgen-mcp/es/configuration/) para la lista completa):

    	```bash
    	docker run -i --rm \
    	  -e LIBGEN_MCP_UNPAYWALL_EMAIL=you@example.com \
    	  -e LIBGEN_MCP_EXTRA_SOURCES=always \
    	  ghcr.io/jmrplens/libgen-mcp:latest
    	```

    	Para el transporte HTTP en streaming quita el `-i` y publica el puerto — la orden por defecto de la imagen es `--transport auto --http 0.0.0.0:8080`, así que no hay nada que pasar. En modo HTTP se expone además un endpoint `GET /health`:

    	```bash
    	docker run --rm -p 8080:8080 \
    	  -v "$HOME/Downloads:/downloads" \
    	  -e LIBGEN_MCP_DOWNLOAD_DIR=/downloads \
    	  ghcr.io/jmrplens/libgen-mcp:latest
    	```

    	Nombrar tú el listener sigue funcionando — `docker run --rm -p 9000:9000 ghcr.io/jmrplens/libgen-mcp:latest --http 0.0.0.0:9000` — con una cosa que conviene saber: **cualquier argumento sustituye la orden por defecto entera**, `--transport auto` incluido. Aquí es inofensivo, porque nombrar un listener es decidir el transporte, pero significa que el flag que añades es la línea de órdenes _completa_ y no un añadido a ella.

    	Dos ajustes que se encuentran en un contenedor y que por separado sorprenden:

    	- Un contenedor que se ata a `0.0.0.0` **con `LIBGEN_MCP_ALLOW_PRIVATE_ADDRESSES` puesto se rechaza al arrancar**, y la orden por defecto de arriba es exactamente ese listener. El rechazo es deliberado — esa variable permite a quien llama dirigir el servidor a direcciones que solo este host alcanza, que no es un poder para entregárselo a quien encuentre el puerto publicado — así que pasa `--http 127.0.0.1:8080` y pon un proxy delante, o deja la variable sin poner.
    	- Un contenedor en el espacio de red **del host** (`--network host`) detrás de un proxy en esa misma máquina se alcanza por loopback, así que al servidor le parece un cliente local. En una red bridge — la de por defecto — no lo es, y lo que llega es la dirección del proxy. Consulta [Remoto (HTTP en streaming)](#remoto-http-en-streaming) para saber qué flags necesita cada forma.
    </TabItem>

### Instalar desde un registro

`libgen-mcp` se publica en los registros de MCP con el identificador
`io.github.jmrplens/libgen-mcp`. Si tu cliente instala servidores desde alguno
de ellos, puedes añadirlo desde ahí en lugar de escribir la configuración a
mano:

| Registro MCP            | Ficha                                                                                                                       |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Registro oficial de MCP | [`io.github.jmrplens/libgen-mcp`](https://registry.modelcontextprotocol.io/v0/servers?search=io.github.jmrplens/libgen-mcp) |
| mcp.so                  | [mcp.so/servers/libgen-mcp-d62341](https://mcp.so/servers/libgen-mcp-d62341)                                                |
| LobeHub                 | [lobehub.com/mcp/jmrplens-libgen-mcp](https://lobehub.com/mcp/jmrplens-libgen-mcp)                                          |

La imagen y el módulo Go también se publican, pero son canales de distribución
y no fichas de MCP — instálalos por las vías descritas arriba:
[Docker Hub](https://hub.docker.com/r/jmrplens/libgen-mcp) y
[pkg.go.dev](https://pkg.go.dev/github.com/jmrplens/libgen-mcp).

La entrada del registro declara además el [endpoint hospedado](#endpoint-hospedado-sin-instalar-nada) y la forma auto-hospedada con `--http` como `remotes`, junto a los seis paquetes de instalación, así que un cliente que lea el registro puede ofrecer cualquiera de los dos sin que copies una URL de esta página.

Una ficha de registro puede ir por detrás de la última publicación; la versión
que describe esta documentación es siempre la de
[`VERSION`](https://github.com/jmrplens/libgen-mcp/blob/main/VERSION).

## Configurar un cliente MCP

Apunta tu cliente al binario. El comando es `libgen-mcp` (o la ruta absoluta al binario `server` si mantuviste el nombre por defecto de `go install`). Sobre stdio no hacen falta argumentos adicionales.

### Claude Code

Añade el servidor al `.mcp.json` de tu proyecto (o ejecuta `claude mcp add`):

```json
{
	"mcpServers": {
		"libgen": {
			"command": "libgen-mcp"
		}
	}
}
```

### Claude Desktop

La vía más sencilla es la extensión **`.mcpb`** de un clic de la [última release](https://github.com/jmrplens/libgen-mcp/releases/latest) (macOS, Windows y Linux, sin Docker): descárgala, ábrela con Claude Desktop y confirma los ajustes. En Linux, instálala desde **Extensions > Install Extension…**, porque la app de Linux no abre los ficheros `.mcpb` por sí misma.

Para configurarlo a mano, edita `claude_desktop_config.json` (`~/Library/Application Support/Claude/` en macOS, `%APPDATA%\Claude\` en Windows, `~/.config/Claude/` en Linux) y añade el mismo bloque `mcpServers`, luego reinicia Claude Desktop:

```json
{
	"mcpServers": {
		"libgen": {
			"command": "/absolute/path/to/libgen-mcp",
			"env": {
				"LIBGEN_MCP_DOWNLOAD_DIR": "/absolute/path/to/downloads"
			}
		}
	}
}
```

<Aside type="caution">
	Los clientes de escritorio no heredan el `PATH` de tu shell, así que usa una
	ruta `command` absoluta.
</Aside>

### VS Code

El soporte MCP de VS Code (o las extensiones Continue / Cline) lee un `mcp.json` con la misma forma. En el formato propio de VS Code:

```json
{
	"servers": {
		"libgen": {
			"command": "libgen-mcp",
			"type": "stdio"
		}
	}
}
```

### Endpoint hospedado (sin instalar nada)

Hay una instancia pública en **`https://mcp.jmrp.io/libgen`**. No necesita cuenta, ni clave, ni ningún proceso local: apunta ahí cualquier cliente MCP capaz de hablar HTTP:

```json
{
	"mcpServers": {
		"libgen": { "type": "http", "url": "https://mcp.jmrp.io/libgen" }
	}
}
```

Es la forma más rápida de probar el servidor. Ejecutarlo **en local** — con Docker o con un binario, más arriba — sigue siendo la mejor forma de usarlo a diario, por dos razones concretas y no como advertencia de rigor:

- **Tus consultas pasan por la máquina de otra persona.** En local, lo que buscas no sale de tu ordenador. La instancia hospedada no guarda nada, pero "no guarda nada" es una promesa; "no se envió nunca" es un hecho.
- **`download` no puede escribir en tu disco desde un servidor remoto**, así que devuelve un enlace (un `resource_link` más un objeto `resolved`) en lugar de guardar un fichero. Eso es inherente al MCP remoto, no una limitación de este endpoint — ver [Dónde acaba el fichero](/libgen-mcp/es/tools/#dónde-acaba-el-archivo-local-vs-remoto).

El endpoint habla el mismo HTTP en streaming sin estado que se describe más abajo: `POST` lleva el protocolo, `GET` sobre el propio endpoint responde `405` a propósito — una ruta que el servidor no sirve responde `404` — y `https://mcp.jmrp.io/libgen/health` responde `{"status":"ok","version":"…","commit":"…","started_at":"…","uptime_seconds":…}`. Su versión sigue las releases de este repositorio, así que puede ir brevemente por detrás de una etiqueta recién publicada.

Es uno de los servidores listados en **[mcp.jmrp.io](https://mcp.jmrp.io/)**, un directorio de los servidores MCP que mantiene el autor, cada uno accesible en su propio endpoint bajo el mismo dominio; [`servers.json`](https://mcp.jmrp.io/servers.json) es esa misma lista para clientes automáticos.

### Remoto (HTTP en streaming)

Para ejecutar el servidor de forma centralizada y conectarte por HTTP en lugar de stdio, inícialo con una dirección y apunta los clientes con capacidad HTTP hacia él:

```bash
libgen-mcp --http :8080
```

El endpoint es el propio montaje — aquí `POST /` — y `POST /mcp` es un alias suyo, porque hay suficientes clientes y guías que dan por hecho esa ruta como para que una URL base pegada con ella o sin ella llegue al mismo sitio. Con `--http-path` el alias se mueve con el montaje (`/libgen/mcp`).

**Detrás de un proxy inverso, declara el nombre que usan los clientes.** Un proxy reenvía el `Host` del cliente y conecta por loopback, y un servidor que nunca oyó ese nombre rechaza la petición con `403` — la comprobación de DNS rebinding que se le pide a todo servidor MCP. Dile el nombre con `--public-url`, o avala al proxy con `--trusted-proxies`; con cualquiera de los dos basta, y ninguno es opcional en un bind comodín, que no declara nombre propio:

```bash
libgen-mcp --http :8080 --public-url https://mcp.example.org
```

**Y nombra el proxy, o todos los llamantes serán uno solo.** Declarar el nombre consigue que la petición se sirva; no le dice a este servidor quién la envió. Detrás de un proxy todas las conexiones vienen del proxy, así que el límite de tasa por llamante y el techo de llamadas en vuelo por llamante pasan a ser un único presupuesto para todo el despliegue hasta que se nombra el proxy y se cree su cabecera:

```bash
libgen-mcp --http 127.0.0.1:8080 \
  --public-url https://mcp.example.org \
  --trusted-proxies 127.0.0.1/32 \
  --trusted-proxy-header X-Real-IP
```

```nginx
location / {
    proxy_pass         http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_buffering    off;   # la respuesta del POST es un flujo SSE real
    proxy_read_timeout 1h;    # las descargas emiten progreso durante minutos
    proxy_set_header   X-Real-IP $remote_addr;
}
```

Los dos flags o ninguno: cualquiera de ellos a solas aborta el arranque. `--trusted-proxies` nombra el par **del que este servidor acepta conexiones**, que detrás de un puerto de contenedor publicado es la pasarela del bridge y no el `127.0.0.1` que usa la línea `proxy_pass`; si te equivocas, la cabecera se ignora en silencio. [Modo servidor HTTP](/libgen-mcp/es/http-server-mode/) recorre las tres formas de despliegue, qué le hace cada una a los límites y cómo leer esa dirección de tu propio despliegue.

En modo HTTP el servidor expone además un endpoint `GET /health` de disponibilidad que devuelve `200` mientras está sirviendo, cómodo para las comprobaciones de salud de contenedores y balanceadores de carga. Responde al `Host` que envíe quien sondea, incluso a ninguno — el `option httpchk` de HAProxy no envía `Host` salvo que se configure, y una sonda rechazada marca como caída una instancia que funciona.

En modo HTTP el servidor publica además **dos server cards**, una por ubicación, porque las dos especificaciones que reservan esas rutas describen documentos distintos:

- `GET /server-card`, servida como `application/mcp-server-card+json`, es la **card de descubrimiento** que describe SEP-2127. Lleva identidad y nada más — el nombre de registro `io.github.jmrplens/libgen-mcp`, la versión en ejecución, la descripción, la web y el repositorio — y, cuando `--public-url` nombra una, una entrada `remotes` con esa URL, el tipo `streamable-http` y las versiones de protocolo que negocia _este_ despliegue. No lista tools ni prompts: lo que expone un servidor puede variar por sesión, así que una card no puede responder eso con honestidad.
- `GET /.well-known/mcp/server-card.json`, servida como `application/json`, es la **card enumerativa** que describía el borrador anterior SEP-1649, y se mantiene porque los escáneres ya la piden ahí. Lleva `serverInfo`, las `capabilities` que negocia el handshake, un bloque `authentication` (este servidor no pide ninguna) y los listados completos de `tools` y `prompts`, de modo que un directorio puede leer toda la superficie — los cuatro prompts incluidos — sin abrir una sesión MCP.

Las dos se sirven sin autenticación, responden al preflight CORS y llevan `Access-Control-Allow-Origin: *` para que también pueda leerlas un directorio que corra en el navegador, y a ninguna le afecta el `405` que el modo sin estado devuelve en el endpoint MCP. Ambas llevan además un `ETag` fuerte derivado de los bytes del propio documento, así que la revalidación pasada la hora de su `Cache-Control` cuesta un `304` en lugar del documento entero — y como la etiqueta depende solo de los bytes, dos réplicas detrás de un mismo balanceador publican la misma.

El transporte es **sin estado por defecto**: no hay `Mcp-Session-Id`, cada POST es una petición completa y `GET`/`DELETE` sobre el endpoint MCP devuelven `405` (`/health` no se ve afectado). Es lo que la versión `2026-07-28` del protocolo MCP exige sobre HTTP, y permite poner cualquier número de réplicas detrás de un balanceador normal, sin enrutado pegajoso. Otras dos opciones ajustan el transporte — `--json-response` devuelve `application/json` en lugar de SSE, y `--max-request-body-bytes` estrecha el límite de 4 MiB del cuerpo:

```bash
libgen-mcp --http :8080 --json-response --max-request-body-bytes 1048576
```

Esas rutas — el endpoint MCP, `/health` y las dos rutas de la card — son toda la superficie HTTP. **Cualquier otra ruta responde `404`**, con un cuerpo JSON que nombra el endpoint que se debería haber pedido; un `405` significa ya solo lo que dice, que se llegó al endpoint MCP con el método equivocado. Si un proxy inverso reenvía su prefijo a este servidor en lugar de quitarlo, monta todo el conjunto bajo ese prefijo con `--http-path`:

```bash
libgen-mcp --http :8080 --http-path /libgen
```

El endpoint pasa a ser `POST /libgen`, la sonda `GET /libgen/health`, y las cards cuelgan también de `/libgen`; `libgen`, `/libgen` y `/libgen/` significan el mismo montaje, mientras que un valor con query, fragmento, segmento `..` o escapes porcentuales se rechaza al arrancar. Toda respuesta — incluidos el `404` y el `405` — lleva `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` y `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`. La card sobrescribe la cabecera de caché con su propia duración de una hora. `Strict-Transport-Security` se les une solo cuando este proceso termina TLS él mismo (`--tls-cert`, más abajo); detrás de un proxy que lo termine, es el proxy quien la envía.

Si algún cliente tuyo todavía necesita el transporte con sesiones anterior, pasa `--stateless=false`; entonces negocia la versión `2025-11-25` del protocolo MCP o anterior. Consulta [Arquitectura](/libgen-mcp/es/architecture/#modo-sin-estado) para lo demás que cambia, incluida la nota sobre la elicitación.

Como un servidor HTTP atiende a clientes en cuyo disco no puede escribir, `download` devuelve un enlace (un `resource_link` más un objeto `resolved`) en lugar de guardar un fichero — en este modo no hace falta que fijes `resolve_only`. Consulta [Herramientas](/libgen-mcp/es/tools/#dónde-acaba-el-archivo-local-vs-remoto) para el detalle.

Un servidor HTTP sirve además **tres** herramientas en lugar de cuatro por defecto: `read` no se registra, porque devolver una página de texto implica traerse el archivo entero por una IP de salida que comparten todos los que usan tu despliegue. Los clientes descargan el enlace que les da `download` y leen el archivo por su cuenta. Si esa salida a internet es tuya y puedes gastarla, `LIBGEN_MCP_SERVER_FETCH=1` vuelve a activar la herramienta — consulta [Configuración](/libgen-mcp/es/configuration/#libgen_mcp_server_fetch).

<Aside type="note">
	Alojar en su lugar un servidor **stdio** — por ejemplo detrás de `mcp-proxy`
	en un catálogo como Glama — también lo coloca en una máquina remota o efímera,
	solo que sin un listener HTTP. Fija `LIBGEN_MCP_REMOTE_DOWNLOADS=1` para poner
	a ese servidor stdio en el mismo modo de descarga remota que `--http` obtiene
	automáticamente.
</Aside>

#### Detrás de un proxy en la misma máquina: un socket unix

Si lo único que habla con este servidor es un proxy inverso en el mismo host, `--http` acepta también una ruta del sistema de archivos y abre ahí un socket unix en lugar de un puerto:

```bash
libgen-mcp --http /run/mcp-libgen.sock
```

La regla es que un valor que contiene `/` es una ruta: `/run/mcp-libgen.sock` y `./mcp.sock` son sockets, mientras que `:8080`, `127.0.0.1:8080` y — a propósito — un `mcp.sock` pelado son direcciones, porque un nombre pelado no se distingue de un nombre de host. Prefiérelo a TLS para un proxy en la misma máquina: no cifra el salto, lo elimina. No hay puente que espiar, ni salto por `docker-proxy`, ni puerto que otro proceso local pueda alcanzar, ni certificado que emitir o rotar.

El socket se crea con `0660` — propietario y grupo, nada más —, así que el proxy llega compartiendo el grupo y no por ser cualquier cuenta local; `--http-socket-mode 0600` (o cualquier otro modo octal) lo cambia. nginx apunta un upstream directamente a la ruta:

```nginx
upstream libgen {
    server unix:/run/mcp-libgen.sock;
}

server {
    listen 443 ssl;
    server_name mcp.example.org;

    location / {
        proxy_pass         http://libgen;
        proxy_http_version 1.1;
        proxy_buffering    off;   # la respuesta del POST es un flujo SSE real
        proxy_read_timeout 1h;    # las descargas emiten progreso durante minutos
        proxy_set_header   X-Real-IP $remote_addr;
    }
}
```

Esa última cabecera solo merece la pena enviarla si al servidor se le dice que la lea. El par de un socket unix es una ruta y no una dirección, así que la confianza se declara con el literal `unix`: `--trusted-proxy-header X-Real-IP --trusted-proxies unix`. Los dos flags o ninguno — cualquiera por separado aborta el arranque — y sin ellos todos los llamantes se distinguen por el socket, es decir, no se distinguen. Sobre TCP, nombra la dirección desde la que el servidor acepta conexiones en lugar de `unix`; detrás de un puerto de contenedor publicado esa es la pasarela del bridge, no el `127.0.0.1` que usa la línea `upstream`.

Con Docker, los dos contenedores comparten el directorio del socket y no publican nada:

```yaml
services:
  libgen-mcp:
    image: ghcr.io/jmrplens/libgen-mcp:latest
    command: ["--http", "/run/mcp/libgen.sock"]
    user: "10001:10001"
    volumes:
      - ./run:/run/mcp # aquí vive el socket; no se publica ningún puerto
  proxy:
    image: nginx:1.29-alpine
    ports:
      - "443:443"
    volumes:
      - ./run:/run/mcp
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
```

Los procesos worker del proxy tienen que correr en el grupo del socket (aquí el GID `10001`) para poder abrir un socket `0660` — en nginx eso es el segundo argumento de la directiva `user`, `user nginx 10001;`, porque nginx reinicializa sus grupos al soltar privilegios.

<Aside type="caution">
	Un socket unix sigue siendo un valor de `--http` no vacío, así que `download`
	se queda en modo remoto (solo enlaces). Es lo correcto — un socket detrás de
	un proxy atiende a clientes que no están en esta máquina —, pero "socket unix"
	se lee como "local" y no lo es.
</Aside>

#### Configurar el listener sin línea de órdenes

Cada opción HTTP tiene además su variable, así que el mismo despliegue se puede escribir sin ningún `command:` — que es con lo que tiene que apañarse un ConfigMap de Kubernetes, el `Environment=` de una unidad de systemd o una imagen que ejecuta por ti la plataforma de otra persona:

```yaml
services:
  libgen-mcp:
    image: ghcr.io/jmrplens/libgen-mcp:latest
    environment:
      LIBGEN_MCP_HTTP_ADDR: "/run/mcp/libgen.sock"
      LIBGEN_MCP_TRUSTED_PROXY_HEADER: "X-Real-IP"
      LIBGEN_MCP_TRUSTED_PROXIES: "unix"
      LIBGEN_MCP_DRAIN_DELAY: "10s"
    user: "10001:10001"
    volumes:
      - ./run:/run/mcp
```

El nombre es el de la opción en mayúsculas y con los guiones como guiones bajos, bajo `LIBGEN_MCP_`. La única excepción es `--http`, cuya variable es `LIBGEN_MCP_HTTP_ADDR`: `LIBGEN_MCP_HTTP` se leería como un interruptor y no como una dirección. La lista completa está en [Configuración → Listener HTTP](/libgen-mcp/es/configuration/#listener-http).

{/* libgen:allow-name LIBGEN_MCP_HTTP: se nombra arriba como la grafia que este servidor deliberadamente no usa */}

**Una opción que teclees sigue ganando**, así que una imagen base que fija sus valores por defecto en `environment:` y un `command:` que sobrescribe uno de ellos se comportan como parece. Teclear una opción cuenta incluso si tecleas su valor por defecto: `--stateless=true` gana a `LIBGEN_MCP_STATELESS=0`, porque la pregunta es si lo pediste, no si la respuesta cambia. Una variable que no se puede interpretar aborta el arranque nombrando la variable y la opción, en lugar de dejar el valor por defecto en silencio — y el log de arranque nombra las variables que configuraron el listener, que es la respuesta más rápida a «¿por qué está en ese puerto?».

#### Terminar TLS en este proceso

Cuando el proxy está en **otro** host sí hay un segmento de red que tiene que existir, y este servidor puede terminar TLS él mismo:

```bash
libgen-mcp --http 0.0.0.0:8443 --tls-cert /etc/ssl/mcp.crt --tls-key /etc/ssl/mcp.key
```

Las dos opciones o ninguna — un certificado sin clave aborta el arranque, igual que un archivo que no se puede leer o una clave que no case con su certificado, porque la pareja se carga al arrancar y no en el primer handshake. **Una renovación escrita en esas mismas dos rutas no exige reiniciar**: cada handshake comprueba si los ficheros se han movido y los relee cuando así es, de modo que certbot, el agente de Vault o un secreto de Kubernetes remontado se recogen en la siguiente conexión, y una pareja a medio escribir conserva el certificado anterior en lugar de hacer fallar el handshake. El listener exige TLS 1.2 o superior y negocia HTTP/2 con los clientes que lo ofrecen. Entonces toda respuesta lleva `Strict-Transport-Security: max-age=31536000; includeSubDomains`, que solo el endpoint que realmente terminó la conexión está en posición de afirmar.

Si el certificado viene de una CA privada, hay que apuntar el proxy de delante a esa CA — en nginx, `proxy_ssl_verify on;` **junto con** `proxy_ssl_trusted_certificate /etc/nginx/ca.pem;` y un `proxy_ssl_name` que case con el certificado. nginx no verifica por defecto los certificados de los upstream, así que dejar `proxy_ssl_verify` desactivado oculta una cadena mala, y activarlo sin el archivo de la CA hace fallar todas las peticiones.

Consulta [Configuración](/libgen-mcp/es/configuration/) para las variables de entorno que puedes fijar en cualquiera de estos casos, [Arquitectura](/libgen-mcp/es/architecture/) para saber cómo funcionan los transportes, y [Modo servidor HTTP](/libgen-mcp/es/http-server-mode/) para las decisiones que un despliegue tiene que tomar por encima de estas recetas: el par de flags del proxy de confianza, el límite de tasa y el techo de llamadas en vuelo, el retardo de drenaje, el digest de configuración y con qué se niega a arrancar el servidor.

## Tu primera búsqueda

<LegalNotice />

Cuando el cliente muestre `libgen` como conectado, pídele que busque. Una petición como:

> Busca "the go programming language" en no ficción, 25 resultados.

acciona la herramienta `search` con más o menos estos argumentos:

```json
{
	"query": "the go programming language",
	"topics": ["nonfiction"],
	"results_per_page": 25
}
```

Cada resultado incluye un `md5` (para libros) o un `doi` (para artículos). Pasa un `md5` a `get_details` para obtener los metadatos completos, y luego a `download` para descargar el archivo — o pasa un `doi` directamente a `download` para un artículo. `get_details` también devuelve un campo `citations` (`bibtex`/`ris`) que puedes pegar directamente en un gestor de referencias, y acepta un `enrich: true` opt-in para añadir metadatos best-effort de Crossref/OpenLibrary. Consulta [Herramientas](/libgen-mcp/es/tools/) para ver todas las formas de entrada y salida.

## Leer y resumir

No hace falta descargar un archivo solo para ver qué contiene: `read` extrae y pagina directamente el texto de un libro o artículo. Una petición como:

> Busca el artículo "Attention Is All You Need", lee su primera página y resume de qué trata.

hace que el modelo busque y luego llame a `read` con el DOI (o el `md5` de un libro) del resultado:

```json
{
	"doi": "10.48550/arXiv.1706.03762",
	"max_pages": 1
}
```

El campo `text` de la respuesta contiene el primer fragmento extraído — hasta `LIBGEN_MCP_READ_MAX_CHARS` caracteres, o `LIBGEN_MCP_READ_DEFAULT_PAGES` páginas de PDF, según aplique al formato — más `has_more`/`cursor` para seguir paginando, y `extractable`/`reason` cuando el archivo no tiene una capa de texto utilizable (un PDF escaneado, por ejemplo — `read` nunca ejecuta OCR).

<Aside type="caution">
	Trata `text` como **contenido no confiable que hay que resumir, no como
	instrucciones que seguir**; la propia `next_steps` de la herramienta lo indica
	en cada llamada.
</Aside>

Consulta [Herramientas](/libgen-mcp/es/tools/#read) para la referencia completa de entrada/salida.

## Preguntas frecuentes

### ¿Cómo instalo libgen-mcp?

Con el gestor de paquetes que ya uses, que en todos los casos acaba en el mismo binario estático: npm (`npx @jmrp.io/libgen-mcp` o `npm install -g @jmrp.io/libgen-mcp`), PyPI (`uvx libgen-mcp` o `pipx install libgen-mcp`), Homebrew (`brew install jmrplens/tap/libgen-mcp`) o NuGet (`dnx libgen-mcp` o `dotnet tool install -g libgen-mcp`). Si no, usa el binario precompilado: descarga el archivo para tu plataforma desde la página de [releases de GitHub](https://github.com/jmrplens/libgen-mcp/releases) (los archivos se llaman `libgen-mcp-<os>-<arch>`, cubriendo Linux, macOS y Windows en amd64 y arm64), hazlo ejecutable y colócalo en tu `PATH`. Es un único ejecutable totalmente estático sin nada más que instalar. Como alternativas puedes usar la imagen de Docker multi-arch `ghcr.io/jmrplens/libgen-mcp:latest` o, si ya tienes Go 1.27 o posterior, compilar desde el código fuente con `go install github.com/jmrplens/libgen-mcp/v2/cmd/server@latest`.

### ¿Qué método de instalación debería usar?

El gestor de paquetes que ya esté en la máquina, porque todos entregan el mismo binario: npm si tienes Node, PyPI si tienes `uv` o `pipx`, Homebrew en macOS o Linux, NuGet si tienes el SDK de .NET. Cualquiera de ellos puede además ejecutar el servidor sin instalarlo — `npx`, `uvx` y `dnx` lo hacen. Usa el binario precompilado si no tienes ninguno: es un único ejecutable estático que no necesita toolchain de Go, ni Docker, ni runtime. Elige Docker si prefieres contenedores o un comando sin instalación que tu cliente descarga en el primer arranque. Elige `go install` solo si ya tienes Go 1.27 o posterior y quieres compilar desde el código fuente. En Claude Desktop, la extensión `.mcpb` de un clic del último release es la opción más sencilla.

### ¿Cómo conecto libgen-mcp a Claude o VS Code?

Apunta tu cliente MCP al binario `libgen-mcp`; por stdio no hacen falta argumentos adicionales. En Claude Code, añade un servidor `libgen` con command `libgen-mcp` al `.mcp.json` de tu proyecto (o ejecuta `claude mcp add`). En Claude Desktop, abre la extensión `.mcpb` de un clic, o añade el mismo bloque `mcpServers` a `claude_desktop_config.json` usando una ruta absoluta en `command`. En VS Code, añade una entrada `libgen` a `mcp.json` con command `libgen-mcp` y type `stdio`.

### ¿libgen-mcp necesita un token o cuenta?

No. libgen-mcp no necesita ningún token, clave de API ni cuenta de Library Genesis para funcionar. Por stdio solo le das al cliente el comando que lanza el binario. Todas las opciones de configuración son variables de entorno opcionales con un valor por defecto seguro, así que el servidor funciona nada más instalarlo.
