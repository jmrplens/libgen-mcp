You talk to the assistant, and the assistant calls the tools. This page walks through seven requests people make, end to end: what to ask, which calls the assistant makes and in what order, and what to look at in the answer. The calls are shown as the arguments the assistant sends, so you can recognise them in a client that displays tool calls, and every argument name is the one [Tools](/libgen-mcp/tools/) documents.

Two things hold for all of them:

- **Results quote third parties.** Titles, descriptions and extracted text are data the assistant reads, never instructions it follows.
- **A remote server returns links.** On the [hosted endpoint](/libgen-mcp/hosted/) or any `--http` deployment, `download` answers with a direct link instead of saving a file. `read` is there only where the operator turned it on, as the hosted endpoint has, and even then it never takes a local `path`.

## Find a specific edition of a book

> Find the third edition of Knuth's _The Art of Computer Programming_, volume 1, as a PDF.

The assistant searches the catalog and sorts so editions are easy to compare:

```json
{
	"query": "Art of Computer Programming Knuth",
	"topics": ["nonfiction"],
	"order": "year",
	"order_mode": "desc"
}
```

Each row carries `year`, `edition`, `extension`, `size`, `pages` and the original `filename`, which is what tells two editions apart when the catalog leaves the year empty. If you know the ISBN, a search on that field alone is narrower:

```json
{ "query": "9780201896831", "search_in": ["isbn"] }
```

Before downloading, `get_details` with the chosen row's `md5` confirms the edition, publisher and ISBNs, and then `download` takes the same `md5`:

```json
{ "md5": "<md5 from the chosen row>" }
```

The answer's `verified: true` means the saved bytes hash to that md5. The `acquire_book` prompt asks for this whole flow in one step, with `title`, and optionally `author`, `format` and `language`.

## Get an open-access copy of a paper

> Download the paper with DOI 10.1038/nature12373.

One call is enough:

```json
{ "doi": "10.1038/nature12373" }
```

`download` offers the DOI to the open-access sources first (OpenAlex, Europe PMC, bioRxiv, Zenodo and the rest), then the fallbacks, and saves the first copy one of them serves. Every step of this, what to set up and what to do on a miss, is in [Download a paper by DOI](/libgen-mcp/download-a-paper/). To try one source and no other, name it, such as `"source": "openalex"`. The `get_paper` prompt takes the same DOI, or a free-text citation instead.

## Survey the literature on a topic

> Find recent open-access papers and a couple of books on retrieval-augmented generation, and build me a reading list.

For papers, the assistant asks beyond the catalog on purpose, because preprints and open-access work often live only there:

```json
{
	"query": "retrieval-augmented generation",
	"topics": ["articles"],
	"extra_sources": "always",
	"year_from": 2023
}
```

`year_from` is what makes it recent. The providers whose APIs can filter by year are asked to, and every other result, the catalog's included, is checked once it arrives, so the range holds across the whole answer. A catalog record with no year is left out and counted in `year_filtered`.

The catalog's matches, and Anna's Archive's, come back as rows, and the other providers' as a separate `open_access` list, each labelled with its `origin`. The origin says what to do next: a `crossref`, `europepmc`, `dblp` or `pubmed` hit carries a DOI for `download`, an `arxiv` hit, and an `openalex` hit whose free copy OpenAlex knows, carries a `pdf_url` the assistant fetches directly, and only a hit marked `open_access: true` claims to be free to read. A second search without `topics` finds the books. [How search works](/libgen-mcp/how-search-works/) explains the labels.

The `research_topic` prompt runs this survey for you, with `topic`, `kind` (`articles`, `books` or both) and `limit`, and asks for an annotated bibliography at the end.

## Build a bibliography

> Give me BibTeX for these three books and RIS for the two papers, for Zotero.

For each item the assistant calls `get_details` with the identifier it already has:

```json
{ "md5": "<md5 from a search result>" }
```

```json
{ "doi": "10.1016/j.cell.2011.02.013" }
```

The record carries a `citations` field with a `bibtex` entry and a `ris` record, plus `doi_status`, which says whether Crossref confirmed the DOI. A DOI that could not be confirmed is left out of the entries rather than pasted into a reference it may not belong to. The Markdown answer shows only the BibTeX, so ask for the RIS explicitly when you want it. Which identifier gives the fullest entry, and why a DOI goes missing, is in [Citations](/libgen-mcp/citations/).

A bibliography in a house style is one argument more:

```json
{ "doi": "10.1016/j.cell.2011.02.013", "cite_as": ["apa", "vancouver"] }
```

`cite_as` takes any of `apa`, `mla`, `chicago`, `harvard`, `vancouver`, `ieee` and `csl-json`, and each style comes back under its own heading saying how it was made. A record whose DOI Crossref confirmed is formatted by the agency that registered the DOI, through doi.org. Any other record, a book found by md5 for instance, has the style built from its own fields, with a part left out rather than guessed when the field is empty.

A reference that arrives as text, copied from a paper's reference list, needs no search first:

```json
{ "citation": "LeCun Y, Bengio Y, Hinton G. Deep learning. Nature 2015" }
```

Crossref resolves it to the DOI of the one work that clearly matches, and the answer names that DOI so you can check it is the work you meant. When no candidate clearly wins, the answer lists the candidates and returns no record, rather than citing a work the text never named.

## Follow a paper's references and citations

> Which papers does _Deep learning_ by LeCun, Bengio and Hinton build on, and which later papers cite it most?

The assistant asks `get_details` for the related works, once in each direction:

```json
{ "doi": "10.1038/nature14539", "related": "references", "related_limit": 10 }
```

```json
{ "doi": "10.1038/nature14539", "related": "cited_by", "related_limit": 10 }
```

Both answers come from OpenAlex: the total it counts, then a table of works with title, year, DOI, an open-access flag and how often each is cited, the most cited first. Every DOI in the table goes straight to `download`, or back into `get_details` to keep walking. `related_limit` runs from 1 to 25 and defaults to 10. A record with no DOI, or one Crossref did not confirm, says the list is not available, since OpenAlex is asked by DOI. With no key the lookups share the daily allowance OpenAlex grants an address, which `LIBGEN_MCP_OPENALEX_KEY` raises.

## Read and summarise one chapter

> Summarise the chapter on amortized analysis in this book, and quote where it defines the potential method.

`read` works without saving the whole book anywhere you have to look. The assistant first asks for the table of contents, top level only:

```json
{ "md5": "<md5>", "outline": true, "max_depth": 1 }
```

The outline numbers each entry and gives its page, and the assistant reads the chapter by its number, or by its title:

```json
{ "md5": "<md5>", "section": "17" }
```

A section read starts where the entry starts and stops where the next entry at the same or a higher level begins, and the answer's `section` field says how far the chapter reaches. When `has_more` is true it passes back the returned `cursor` for the next chunk of the same chapter, and `has_more` turns false at the chapter's end rather than the book's. A title that matches more than one entry, such as a recurring "Exercises", is refused with the matching entries listed, so the assistant can pick one by number. To find one passage rather than read sequentially, it searches inside the document:

```json
{ "md5": "<md5>", "find": "potential method", "max_matches": 5 }
```

Each match comes with its page and a snippet. A book you already downloaded is read by `path` instead of `md5`, as long as it is inside the working, temp or download directory. A scanned book with no text layer comes back `extractable: false`: there is no OCR.

<Aside type="note">
	Reading by `path` needs a local server. The [hosted
	endpoint](/libgen-mcp/hosted/) reads by `md5` or `doi` only. On a remote
	deployment that does not serve `read` at all, the assistant downloads the link
	`download` returns with its own fetch tool and reads the file locally instead.
</Aside>

## Check what a reference points to

> This reference list cites 10.1371/journal.pmed.0020124 for _Antifragile_. Is that right?

The assistant looks the DOI up rather than trusting it:

```json
{ "doi": "10.1371/journal.pmed.0020124" }
```

The answer shows the title of the record the DOI reaches, and `get_details` asks Crossref which title it registers that DOI to. Here they disagree: Crossref registers it to Ioannidis's paper _Why Most Published Research Findings Are False_, so a record pairing it with the book comes back `doi_status: "mismatch"`, and its `provenance` line names the real work. When the catalog does not carry a DOI at all, Crossref's own metadata stands in, labelled `origin: "crossref"`, and a DOI Crossref does not know either, a DataCite dataset or a mEDRA article, gets the record its own registry serves through doi.org, labelled `origin: "doi.org"`. For a reference with no DOI, `get_details` with the reference as `citation` finds the DOI it names, or lists the candidates to compare when none clearly matches.
