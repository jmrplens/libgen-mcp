`libgen-mcp` is configured through environment variables. Every variable is optional: an empty or unset value uses the documented default.

<Aside type="caution">
	A variable that is present but malformed (a bad number, an out-of-range value,
	an unwritable directory, an unknown source name) causes the server to **fail
	fast at startup** with an explanatory error rather than silently falling back
	to the default.
</Aside>

There are three places a setting can come from, and they are tried in this order — the first one where the variable is **set** wins, which is not quite the same as the first one that has a value:

1. **The process environment**, which is what your MCP client passed. Set these in the client's `env` block (see [Getting started](/libgen-mcp/getting-started/)), in your shell, or with `-e` flags on `docker run`. A handful also have flags; see below.
2. **The file `LIBGEN_MCP_ENV_FILE` names**, if you named one. Give it an absolute path.
3. **`~/.libgen-mcp.env`**, a dotenv file in your home directory.

<Aside type="caution">
	**An exported variable with an empty value is set, and it wins.** A dotenv
	file only fills in names the process environment does not already carry, so
	`LIBGEN_MIRROR=` in a client's `env` block — or a `-e LIBGEN_MIRROR` on
	`docker run` with nothing after it — suppresses the value in both dotenv files
	and the setting falls back to its documented default. That is the right
	behavior (an empty value is something you said) and it is the one that
	surprises people, because the file is there and reads correctly. To let a file
	supply a variable, leave it out of the environment entirely rather than
	setting it to nothing.
</Aside>

<Aside type="danger">
	**A `.env` in the working directory is never loaded.** When one is there the
	server names it and its keys at startup and carries on without it. A stdio
	server inherits its working directory from the client, and every client that
	opens a workspace sets it to that workspace — so the file's contents arrive
	with a cloned repository rather than from you. A two-line `.env` could point
	`LIBGEN_MIRROR` at a host of its choosing, open the outbound address guard, or
	widen the directories `read` accepts, and none of it would need a tool call or
	a model turn. To have a repository-local file configure the server, name it:
	`--env-file /abs/path/.env`, or the variable.
</Aside>

A few settings also have flags, which are written into their variables only when you actually type them — so an exported value survives a flag you did not pass: `--log-level`, `--download-dir`, `--mirror`, `--sources`, `--allow-private-addresses`, `--pprof-addr` and `--env-file`. The credential-shaped settings (`LIBGEN_MCP_ANNAS_KEY`, `LIBGEN_MCP_CORE_KEY`, `LIBGEN_MCP_UNPAYWALL_EMAIL`) deliberately have none: a secret on a command line is visible to every user on the machine through `ps` and lands in your shell history.

The **HTTP listener settings** go the other way — the flag is the primary spelling and the variable fills it in — but the precedence is the same one: a flag you typed wins, then the environment, then the default. They are listed under [HTTP listener](#http-listener) below.

### HTTP listener

These configure the HTTP transport, and every one of them is the flag of the same name with a variable underneath it. The naming rule is mechanical — `LIBGEN_MCP_` plus the flag in upper case with dashes as underscores — with one exception: `--http` is `LIBGEN_MCP_HTTP_ADDR`, because `LIBGEN_MCP_HTTP` would read as a switch rather than as an address.

They exist for the deployment that has no command line to write on: a compose file's `environment:`, a systemd unit's `Environment=`, a Kubernetes ConfigMap. What each setting _does_ is documented once, with the flags, in [Architecture → Stateless mode](/libgen-mcp/architecture/#stateless-mode) and [Where the server listens](/libgen-mcp/architecture/#where-the-server-listens).

Three details are worth knowing before you rely on them.

**"Explicitly passed" means typed, not different from the default.** A deployment that spells its configuration out in full — `--stateless=true` on an image whose environment sets `LIBGEN_MCP_STATELESS=0` — gets the flag, because the question is whether you asked for it and not whether the answer happens to match. It goes the other way too: exporting `LIBGEN_MCP_RATE_LIMIT_RPS` counts as asking for that limit, so a listener that cannot tell two callers apart refuses to start rather than quietly ignoring it, exactly as it does for the flag.

**A value that does not parse fails startup**, naming the variable and the flag it fills. Falling back to the default in silence is how a deployment that does not match its own configuration reaches production looking healthy.

**A variable that is set but blank counts as unset**, which is what `${FOO}` expands to in a compose file when the shell has no `FOO`. Surrounding whitespace is trimmed, so a value copied with a trailing space is not a path that does not exist.

## Notes on specific variables

### `LIBGEN_MIRROR`

When set, this mirror is used as the sole preferred mirror and is placed first. It must parse as an `http`/`https` URL with a host, otherwise startup fails. Leave it unset to let the server discover the current live mirrors and fail over between them automatically.

### `LIBGEN_MCP_DOWNLOAD_DIR`

At startup the directory is created (with mode `0750`) if it does not exist and a temporary file is written and removed to confirm it is writable. Under Docker, the container runs as UID `10001`, so a mounted host directory must be writable by that user.

### `LIBGEN_MCP_TIMEOUT` and `LIBGEN_MCP_RESOLVE_BUDGET`

These two bound different things, and they used to be one setting.

`LIBGEN_MCP_TIMEOUT` bounds a **single** HTTP request that asks a question. Every such request has failover behind it — another mirror, another source — so hanging on one is pure loss, which is why the default is only `10s`. A live run measured three separate requests hanging for the full 30 seconds the old default allowed, each followed by another mirror that answered immediately: 90 seconds of nothing. Raise it on a slow link.

`LIBGEN_MCP_RESOLVE_BUDGET` bounds a **whole** resolve: everything one download source does to turn an item into a direct file URL. That is often several sequential requests, so it defaults to `30s`. Deriving it from the request timeout, as earlier versions did, coupled the two: shortening the timeout silently cut every source's resolve budget with it, which can strike a slow but working multi-hop source out of a chain it would otherwise have served.

<Aside type="note">
	Neither setting applies to the transfer of a file. A stream is governed by the
	request context and by the progress-resetting
	`LIBGEN_MCP_DOWNLOAD_STALL_TIMEOUT`.
</Aside>

### `LIBGEN_MCP_UNPAYWALL_EMAIL`

`LIBGEN_MCP_UNPAYWALL_EMAIL` is used only by the `unpaywall` source (article DOIs). It is **unset by default, which disables the `unpaywall` source**: the Unpaywall API requires a contact email on every lookup, so without one there is nothing to send and the source is skipped. Set your own contact address to enable it. A non-empty value is sanity-checked (must contain `@` and a dotted domain) but not verified for deliverability; an empty value is allowed and simply leaves the source disabled.

<Aside type="tip">
	When it is unset and a `download` call requests an article by `doi` (with no
	`source` pinned), a client that advertises the MCP **elicitation** capability
	may be asked on demand for a contact email to use for that single request — it
	is used only for that call and is never stored or written back to this
	variable. A client without elicitation, or a decline/ empty/invalid answer,
	leaves this behavior unchanged: `unpaywall` stays disabled and the rest of the
	chain — the keyless open-access sources, then `scihub`/`scidb` — is tried. See
	[Tools](/libgen-mcp/tools/#interactive-prompts-elicitation).
</Aside>

### `LIBGEN_MCP_DOWNLOAD_START_RETRY_WAITS` and `LIBGEN_MCP_DOWNLOAD_STALL_TIMEOUT`

These two variables make downloads resilient without ever cutting a healthy but slow transfer:

- **Getting started** is retried on a staged schedule. A download must first _begin_ — resolve a fresh URL, connect, and yield its first byte. If any of that fails (resolve error, connection error, non-2xx status, or a 2xx that yields no bytes), the attempt is retried after the next wait in `LIBGEN_MCP_DOWNLOAD_START_RETRY_WAITS`. The default `5s,5s,5s,10s,10s,10s,15s` makes 8 attempts over roughly 60 seconds; each retry resolves afresh, so an expired key is renewed. This wraps a single source; the multi-source chain still advances to the next source when one is exhausted. When every source fails to start, the tool returns an actionable error telling the model it can retry now, retry later, or ask the user.
- **Staying alive** is governed by `LIBGEN_MCP_DOWNLOAD_STALL_TIMEOUT`, a _progress-resetting_ window. Once bytes are flowing, the transfer is aborted only if **no** new bytes arrive within the window; every received byte resets the clock. A 30 kB/s download that takes many minutes is never killed, while a truly stalled connection is dropped after the window and its `.part` is kept for a later resume. The per-request `LIBGEN_MCP_TIMEOUT` never applies to a streaming download.

The schedule is spent on the **last** source that can serve the item, not on each one in turn. A source with another behind it gets a single attempt, so a source that is down does not hold up one that is not — a download the next source answers in seconds would otherwise wait out the whole schedule first. Set `LIBGEN_MCP_DOWNLOAD_RETRY_EVERY_SOURCE=true` to give every source the full schedule.

### `LIBGEN_MCP_CORE_KEY`

Unset by default, which leaves the `core` source out of the chain entirely (and hides it from the download tool's `source` schema), exactly as an empty `LIBGEN_MCP_UNPAYWALL_EMAIL` does for `unpaywall`. [CORE](https://core.ac.uk) aggregates open-access research papers; a **free** registered API key enables the source. When set, the key is sent as a Bearer token **only** to `api.core.ac.uk` — never with the resolved file URL — so it does not leak to the CDN that serves the bytes. Keep it out of version control; prefer your MCP client's `env` block or a gitignored env file.

### `LIBGEN_MCP_SOURCES` and the source chain

The download chain always runs in the fixed order <SourceChain variant="arrow" />. Each source declares which items it supports, so in practice:

- **Books** (identified by `md5`) are tried against `libgen`, then `randombook`, then `annas`.
- **Books** (identified by `isbn`) are tried against the open-access book sources `oapen`, then `archive`. Both serve only openly licensed or public-domain copies.
- **Articles** (identified by `doi`) are tried against the legal open-access providers first — `unpaywall` (only when `LIBGEN_MCP_UNPAYWALL_EMAIL` is set), then `openalex`, `europepmc`, `biorxiv`, `rfc` (RFCs), `nist` (NIST publications), `dagstuhl` (Dagstuhl proceedings), `acl` (ACL Anthology papers), `zenodo` (Zenodo deposits), `scielo` (SciELO Brazil articles) and `fao` (FAO Knowledge Repository documents), then `fatcat`, `core` (only when `LIBGEN_MCP_CORE_KEY` is set) — then `crossref`, which is not an open-access index but the publisher's own deposited full-text link, probed before use, and `oapen` (monographs carry DOIs too) — then the shadow-library fallbacks `scihub` and `scidb`.

The two open-access **book** sources are keyless as well. `oapen` submits the DOI or ISBN to the [OAPEN](https://library.oapen.org) DSpace REST API, then checks the candidate record's own `oapen.identifier.doi`/`.isbn` against what was asked for before serving its ORIGINAL-bundle PDF — OAPEN's search is free text, so an identifier it does not hold still returns a page of unrelated monographs. `archive` asks [OpenLibrary](https://openlibrary.org) which [Internet Archive](https://archive.org) scans hold the ISBN and then confirms each candidate with archive.org itself: a book must be `ebook_access: public` **and** its individual scan must carry no `access-restricted-item` flag and no lending collection. Both gates matter, because a work can be publicly readable while a particular scan of it is a controlled-digital-lending copy that advertises ordinary `.pdf`/`.epub` files and serves a DRM-wrapped one.

The open-access article sources are all keyless (except `core`, which needs a free key): `openalex` takes the best open-access location OpenAlex knows for a DOI, reading the same index as Unpaywall but without needing a contact email; `europepmc` fetches an article's PDF from Europe PMC when it holds the open-access full text; `biorxiv` resolves `10.1101` preprint DOIs to the versioned `.full.pdf` on bioRxiv/medRxiv; `rfc` turns the RFC number in a `10.17487` DOI into the RFC Editor's plain-text URL, with no request of its own; `nist` passes a `10.6028` DOI to the DOI resolver, whose redirect ends at the PDF in NIST's repository; `dagstuhl` reads the DROPS document page for a `10.4230` DOI and takes the PDF it advertises, which is the only route to the file because DROPS storage paths embed a volume number the DOI does not carry; `acl` builds the ACL Anthology PDF URL from the identifier a `10.18653`/`10.3115` `/v1/` DOI already contains, uppercasing a volume-lettered identifier and leaving a year-prefixed one alone because the Anthology answers 404 to the other spelling; `zenodo` lists a `10.5281/zenodo` record's files and serves the best one, retrying a concept DOI against the version its record page redirects to; `scielo` follows a `10.1590` DOI through the resolver to its article page on SciELO and takes the PDF from that page's `citation_pdf_url` meta tag, a hop that cannot be skipped because the registered URL is a legacy `scielo.php?pid=` address that redirects on to a `/j/<journal>/a/<key>/` address whose key appears in no identifier the caller holds; `fao` derives the item page in the FAO Knowledge Repository from a `10.4060` DOI's own suffix, which is also the item's handle, and rewrites the `citation_pdf_url` the page advertises into the repository's bitstream _content_ endpoint — a required rewrite, since the advertised URL is an Angular frontend route that answers a plain HTTP client with the application shell rather than the file; `fatcat` looks a DOI up on Internet Archive Scholar and takes the preserved full-text URL its release page advertises — a Wayback capture of the publisher's PDF — probing candidates in page order so a capture that has gone bad falls through to the next one; and `core` returns CORE's download URL when CORE hosts a live copy (the URL is liveness-probed first, since CORE's links go stale often).

`scidb` serves scholarly articles through Anna's Archive's SciDB viewer. It is fully keyless and sits after `scihub` because it reaches papers published after Sci-Hub stopped indexing, covering that gap rather than replacing it.

`annas` is the last book rescue and is keyless by default: Anna's book pages publish each item's IPFS CID, and the source streams from the first public IPFS gateway that serves it. Gateway availability varies widely, so treat it as a genuine fallback rather than a fast path — expect it to be slow, or to time out, for items that are not well seeded. Setting `LIBGEN_MCP_ANNAS_KEY` makes it try the much faster member API first, with IPFS still the fallback.

`LIBGEN_MCP_SOURCES` only removes sources from that chain; it never reorders it. For example, `LIBGEN_MCP_SOURCES=libgen` disables the article sources and the `randombook` fallback, leaving only the primary LibGen book source. See [Architecture](/libgen-mcp/architecture/) for how the chain is built and traversed.

### `LIBGEN_MCP_REMOTE_DOWNLOADS`

Puts the server into the same **remote download mode** that `--http` triggers automatically, but for the **stdio** transport. This matters for a hosted stdio deployment — for example the server running behind `mcp-proxy` on a catalog like Glama — where the process runs on a remote or ephemeral machine whose disk the client cannot reach, so saving a file there is useless. When set to a truthy value, every `download` call always returns a link (a `resource_link` content block plus a `resolved` object, including any required `headers`) instead of writing to disk, exactly as it already does under `--http`. Accepts `1`/`true`/`0`/`false`; any other value fails startup. See [Tools](/libgen-mcp/tools/#where-the-file-goes-local-vs-remote).

Remote mode is decided by `--http` being set at all, not by what it is set to — **a unix socket path counts**. That is worth stating because "unix socket" reads like "local" and is not: a socket is served through a reverse proxy, and the clients on the far side of that proxy are no more able to receive a file written here than the ones behind a TCP port.

### `LIBGEN_MCP_SERVER_FETCH`

Decides whether the server may pull a file's **bytes** over its own internet connection. It is off by default on a remote deployment and on by default on a local stdio one, and an explicit value wins in either direction.

With it **off**:

- the `read` tool is **not registered**. It disappears from `tools/list` rather than appearing and failing every call, because a tool a model can see is a tool it will call, and each attempt would cost a turn to learn what the list could have said for free. The handshake instructions drop its step too.
- `download` always returns a link (a `resource_link` plus a `resolved` object), even on a local server — writing the file to disk is a fetch like any other.
- `search`, `get_details` and `download`'s **link resolution** keep working.

The reason for the remote default is operational, not stylistic. A hosted server reaches the mirrors over an egress IP shared by every user it serves, so one caller's multi-megabyte transfers can get that address throttled or blocked and take the deployment down for everybody. When the client fetches the file instead, a block lands on whoever provoked it. On a local stdio server the connection and the disk are the user's own, and fetching the file is exactly what they asked for.

<Aside type="note" title="Resolving a link is deliberately still allowed">
	`download` does talk to the mirrors to produce its URL — LibGen's `key=` token
	is read off `ads.php`, `randombook` discovers a mirror first — and
	`search`/`get_details` query the catalogs outright. All of that stays on. The
	property at stake is about sustained multi-megabyte transfers, not a handful
	of small HTML and redirect requests; without resolution `download` could not
	work at all; and the catalog queries cannot move client-side without emptying
	the server of its purpose. The rule is precise: **the file body stays on the
	client's side of the connection; everything lighter than that does not move.**
</Aside>

Set `LIBGEN_MCP_SERVER_FETCH=1` on a hosted deployment to accept the egress cost and get `read` back — for example on a private instance, or one whose egress is not shared. Set `LIBGEN_MCP_SERVER_FETCH=0` on a local server to keep it from fetching files at all. See [Tools](/libgen-mcp/tools/#read-is-not-on-every-deployment).

### `LIBGEN_MCP_READ_MAX_CHARS` and `LIBGEN_MCP_READ_DEFAULT_PAGES`

These bound how much text a single `read` call returns by default: `LIBGEN_MCP_READ_MAX_CHARS` caps EPUB/TXT chunks by character count, `LIBGEN_MCP_READ_DEFAULT_PAGES` caps PDF chunks by page count. Both are only fallbacks — a call's own `max_chars`/`max_pages` argument always takes precedence when set to a positive value. Raise them to return more text per call (fewer round trips, more tokens per response) or lower them to keep individual responses small. See [Tools](/libgen-mcp/tools/#read) for the full `read` reference.

### `LIBGEN_MCP_READ_CACHE_BYTES` and `LIBGEN_MCP_READ_CACHE_TTL`

`read` fetches an `md5`/`doi`-identified file to a server-side temp file once, then serves successive pages/chunks from that same file as the model pages through it with `cursor` — without this cache, every page would re-download the whole file. `LIBGEN_MCP_READ_CACHE_TTL` is how long an unreferenced temp file lingers after its last use before eviction; `LIBGEN_MCP_READ_CACHE_BYTES` is the cache's total-size ceiling, past which the least-recently-used files are evicted first (a file a `read` call is actively using is never evicted). Neither variable affects `download`, which always writes directly to `LIBGEN_MCP_DOWNLOAD_DIR` and keeps no server-side temp cache.

### `LIBGEN_MCP_CONFIRM_DOWNLOADS`

Controls whether `download` asks before writing a file to the server's disk. The default `true`
keeps the confirmation; `false` saves without ever prompting.

It is only ever consulted when the connected client advertised the elicitation capability — a
client that cannot be asked is never prompted, whatever this is set to.

`LIBGEN_MCP_CONFIRM_DOWNLOADS` is the deployment-wide switch. Two narrower opt-outs sit alongside it, and any one of them
is enough to skip a given prompt:

- The **"stop asking for the rest of this session"** checkbox on the prompt itself, which is how
  a user turns the prompt off at runtime without restarting the server. It is scoped to the
  client session, so a later connection is asked again. This variable is not a persisted form
  of that choice: setting it `false` disables the prompt for every client and every session,
  rather than remembering what one user ticked.

None of the three can force a prompt to appear — they only remove it.

### `LIBGEN_MCP_ENRICH`

Controls whether `get_details`' opt-in `enrich: true` argument is honored at all. The default `true` means a caller _may_ request enrichment (it still stays off unless a call sets `enrich: true`); setting it to `false` makes the server ignore `enrich` entirely, so no Crossref/OpenLibrary calls are ever made on this deployment. Use this to fully disable outbound calls to those two third-party APIs, for example in a locked-down or offline-preferring deployment. See [Tools](/libgen-mcp/tools/#metadata-enrichment) for what enrichment adds and its 6-second best-effort budget.

### `LIBGEN_MCP_EXTRA_SOURCES`

Controls when the extra searchers (Anna's Archive, arXiv, Crossref, OpenLibrary, Project Gutenberg, dblp, PubMed, ERIC) are consulted. The default `auto` consults them only when the Library Genesis catalog returns nothing or fails; `always` consults them on every search, concurrently with the catalog; `never` restricts every search to the catalog, even on a miss. A per-call `extra_sources` argument overrides this default in either direction, with one exception: a deployment set to `never` is a **lock**, not a default — no call can re-enable the extras, because a policy an individual caller can overrule is not a policy. All eight providers are keyless (no account or API key) and best-effort, each bounded by its own short per-request budget so a slow or failing provider never delays or fails the core Library Genesis search. Anna's md5-keyed hits merge into `results` (labeled by `origin`); the rest appear in the separate `open_access` array, where only an entry with `open_access: true` is known to be free to read — dblp and PubMed are bibliographic indexes, and ERIC hosts only part of what it indexes. See [Tools](/libgen-mcp/tools/#open-access-discovery) for the output shape.

### `LIBGEN_MCP_TELEMETRY` and the `OTEL_*` variables

`LIBGEN_MCP_TELEMETRY` is the only switch this server owns. Everything about _how_ the export happens — the collector endpoint, the protocol, headers, timeouts, sampling, batch sizes, resource attributes, the service name — comes from the standard `OTEL_*` variables, which the OpenTelemetry SDK reads for itself.

**Those names are never prefixed, and that is not an inconsistency.** Every variable this server defines carries `LIBGEN_MCP_`, because a stdio server runs in whatever shell its client was started from, beside every other tool that person uses, and a bare `TIMEOUT` may already belong to one of them. An `OTEL_*` name is not ours to choose: the SDK reads the spelling the specification gives it, so `LIBGEN_MCP_OTEL_EXPORTER_OTLP_ENDPOINT` would be a variable nothing reads. The same applies to `LIBGEN_MIRROR`, which follows the mirror family's own convention.

{/* libgen:allow-name LIBGEN_MCP_OTEL_EXPORTER_OTLP_ENDPOINT: named above as the prefixed spelling nothing reads */}

Two consequences worth knowing before you set them:

- **They are shared with every other OpenTelemetry process in the same environment.** One `OTEL_EXPORTER_OTLP_ENDPOINT` in a compose file configures this server and the sidecar next to it, which is usually what you want and occasionally a surprise. The per-signal forms (`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` and its siblings) are the way to differ.
- **`OTEL_SDK_DISABLED` vetoes the switch**, and is parsed under the specification's grammar — the case-insensitive word `true`, and nothing else — rather than this server's looser one. It cannot be the _on_ switch, because its specified default means "the SDK is enabled" while telemetry here is off until asked for; so the two compose, with ours turning the export on and the specification's able to turn it off from outside.

What is exported, and what is deliberately not, is in [Privacy](/libgen-mcp/privacy/) and in the identity rows above. When telemetry is on, the deployment also says so in its own server card, so a caller of a public endpoint can see that their calls are instrumented without having to ask.

## Frequently asked questions

### What is the minimum configuration for libgen-mcp?

None. `libgen-mcp` is configured entirely through environment variables, and every one is optional with a safe default, so the server runs with no configuration at all. You only set a variable when you want to change a default — for example the download directory, the request rate, or the Unpaywall contact email. A variable that is present but malformed (a bad number, an out-of-range value, an unwritable directory, or an unknown source name) makes the server fail fast at startup with an explanatory error rather than silently falling back to the default.

### How do I change where libgen-mcp saves downloads?

Set `LIBGEN_MCP_DOWNLOAD_DIR` to the destination directory; it defaults to `~/Downloads`. The directory is created if missing and probed for writability at startup. You can also override the destination per call with the `download` tool's `path` argument. Under Docker the container runs as UID `10001`, so a mounted host directory must be writable by that user.

### How do I download research papers by DOI with libgen-mcp?

Pass a `doi` to the `download` tool. Articles are fetched by DOI through seventeen sources in a fixed order, open access first: `unpaywall`, which returns a PDF only when the article is genuinely open access, then `openalex` (the same open-access index, keyless), then `europepmc`, then `biorxiv` for `10.1101` preprints, then `rfc` for `10.17487` RFCs, `nist` for `10.6028` NIST publications, `dagstuhl` for `10.4230` Dagstuhl proceedings, `acl` for `10.18653`/`10.3115` ACL Anthology papers, `zenodo` for `10.5281/zenodo` deposits, `scielo` for `10.1590` SciELO Brazil articles and `fao` for `10.4060` FAO Knowledge Repository documents, then `fatcat` (Internet Archive Scholar) and `core`; then `crossref`, which is not an open-access index but the publisher's own deposited full-text link, probed before use, and `oapen` (monographs carry DOIs too), and only then the shadow-library fallbacks `scihub` and `scidb` (the Anna's Archive SciDB viewer). Two of them are gated on a setting: `unpaywall` is disabled unless `LIBGEN_MCP_UNPAYWALL_EMAIL` is set to a contact address, because the Unpaywall API rejects lookups without an email, and `core` is disabled unless `LIBGEN_MCP_CORE_KEY` holds a (free) CORE API key. The other fifteen need no configuration. You can adjust the Sci-Hub mirrors tried with `LIBGEN_MCP_SCIHUB_HOSTS`, a comma-separated list of bare hosts. Note that DOI downloads are not MD5-verified.

### How do I limit the request rate in libgen-mcp?

`libgen-mcp` uses a shared token-bucket rate limiter across all mirror requests and downloads. Set `LIBGEN_MCP_RATE_RPS` to the allowed requests per second (default `1`, range `(0, 20]`) and `LIBGEN_MCP_RATE_BURST` to how many requests may fire back-to-back before throttling (default `1`, range `[1, 100]`). Lower values are gentler on mirrors; higher values speed up bursts of requests.
